Formatta

Assembling, checking and exporting structured documents from your own sources — with AI only where meaning is needed, and plain code everywhere else.

I designed the product and its architecture and built most of it: the assembly pipeline, the job queue, the chat editor and all export renderers. This page explains how it works and why it is built this way.

2026 Capstone, AI bootcamp Team of 3 Role: product & architecture, lead developer Python · FastAPI · HTMX · SQLite · local LLMs

The problem

FAQs, use cases, specifications and release notes are written the same way over and over: find the facts across several files, move them into the agreed structure, notice what is missing, align terms and style, format to the corporate standard — and redo part of it when another output format is needed.

A chat model can produce a text once. It cannot run this as a repeatable process: it does not keep sources, does not check the document against requirements, and happily fills gaps with plausible inventions.

What it does

Assemble

Build a new document from uploaded sources by a content template. Missing facts become explicit gaps, not guesses.

Check

Review an existing document against the template: structure by code, completeness and consistency by the model.

Convert

Turn one source into another format without rewriting the content.

Sources: DOCX, PDF, TXT, Markdown, images and Confluence pages. Output: DOCX, PDF, HTML, Markdown — with the same content, edited by hand or through chat.

The core idea: three things kept apart

In an ordinary office document, what must be said, what is currently written and how it looks are mixed in one file. Formatta separates them — and the rest of the design follows from that.

Because the document lives in a neutral model, the same text can be checked, edited by hand or through chat, and exported to any format — without generating it again.

Architecture

A modular monolith with a separate background worker. The web process only validates requests and queues jobs; the worker runs extraction, assembly, checks and export.

Key decisions

A neutral document model instead of editing DOCX

Problem
Chat edits, checks and exports all need to work with the same document.
Options
Edit the Word file directly, or keep the document as a format-neutral tree of nodes.
Choice
A neutral model. DOCX is an archive of XML files — a poor domain model that would tie every feature to one format. With a neutral tree there is one editor, one check path and several independent renderers.

Code where it can be exact, the model where meaning is needed

Problem
Some checks must be reproducible, others require understanding.
Choice
Whether a heading or a table column exists is checked by code — exactly and every time the same. Completeness, terminology and contradictions are checked by the model. Storage, validation, versioning and export never touch the model at all.

Long jobs off the HTTP request

Problem
Assembly and export take time; inside a request the connection drops and a second click duplicates work.
Choice
A job queue with leases and heartbeats, progress, cooperative cancellation and safe recovery after a crash; one active job per project. A deliberate MVP trade-off: minimal infrastructure now, a dedicated broker later.

Missing facts stay visible

Problem
A model fills gaps with plausible text.
Choice
The system works only from the user's own sources and shows what is missing instead of inventing it — the user sees the gaps and fills them.

Where AI is used — and where it is not

AI is used only where meaning is needed: understanding sources, judging content against the template, turning a request in chat into an edit. Storage, structure checks, versioning, conversion and export are plain, deterministic code. Models run locally and can be swapped without changing the workflow.

Honestly about hallucinations. The design reduces the risk and keeps every change traceable to the sources; it does not claim to prove every sentence.

What is not solved yet

  • Single-user MVP: no sign-in, roles or per-project access yet.
  • No version history with comparison and rollback.
  • Built for typical documents; very large documents and batch runs are out of scope.
  • Scaling to many users would need a server database and a dedicated job broker.
